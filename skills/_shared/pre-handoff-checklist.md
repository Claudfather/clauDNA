# Pre-Handoff Checklist

Run `/adversarial-review` on your output before emitting. This is the shared gate for all skills that produce planning documents, audit reports, or remediation plans. Skills reference this file instead of inlining the `/adversarial-review` procedure.

---

## When to Run

Run `/adversarial-review` on plan output in **all modes** — interactive, `--output github`, `--output session`, and `--auto`. The gate applies whenever a skill produces a plan document or structured audit finding that will be consumed downstream (by `/claudna:implement-plan`, by a human reader, or as a GitHub Issue body).

Skip only if the skill's plan-generation phase produced zero documents (nothing to review).

---

## Procedure

For each plan document generated by the skill (phase docs, master docs, issue bodies):

1. **Run** `/adversarial-review --dispatch <doc-path>`. The `--dispatch` flag handles context isolation internally — it suppresses interactive elements, spawns parallel critic subagents, and emits a structured markdown document (YAML frontmatter + body). No subagent wrapper needed; the skill manages its own execution model.

2. **Collect** the markdown output. Read the YAML frontmatter for `outcome`. If `outcome` is `completed`, extract findings from the body sections (Blockers, Risks, Gaps, Questions, Observations).

3. **Append** an `## Adversarial Review Findings` section to the document with findings as markdown checkbox bullets:

   ```markdown
   ## Adversarial Review Findings

   These concerns were raised by /claudna:adversarial-review at plan-creation time.
   Items are OPEN until resolved during implementation challenge round or by --auto synthesis pass.

   - [ ] **[<severity>] <concern_area>**: <summary>
     - **Recommendation:** <recommendation>
   ```

   Findings sorted by severity (critical > major > minor > info).

4. **On failure:** if `outcome` is `blocked` or `errors` is non-empty, log a note in the orchestrator session but proceed with the next document. `/adversarial-review` failure does not block plan publishing.

---

## Parallelism

When reviewing multiple documents, launch `/adversarial-review --dispatch` invocations in parallel using `run_in_background: true`, then collect results one at a time. `/adversarial-review --dispatch` manages its own internal parallelism (parallel critic subagents) — the caller only parallelizes across documents.

---

## `--output github` Adaptation

When plan output is GitHub Issues (not phase docs on disk), run `/adversarial-review` on the proposed issue body BEFORE creating the issue:

1. Write the body to a temporary scratch file at `<scratch>/issue-<N>-body.md`.
2. Run `/adversarial-review --dispatch <scratch-path>`.
3. Fold findings into the body.
4. Create the issue with the augmented body.

---

## Skill-Specific Concern Areas

`/adversarial-review --dispatch` emits findings as markdown bullets tagged with `concern_area` values (`architecture`, `testing`, `dependencies`, `error-handling`, `performance`, `security`, `data-integrity`, `compatibility`, `observability`, `scope`). Skills with domain-specific concerns should add a short section after referencing this checklist specifying which `concern_area` values critics should prioritize. Examples:

- **Security skills:** `security`, `data-integrity`, `error-handling`
- **Performance skills:** `performance`, `compatibility`, `architecture`
- **Access-path skills:** `architecture`, `compatibility`, `security`

---

## What Passes

`/adversarial-review` is informational, not blocking. Findings are folded into the plan document as open checklist items. Downstream consumers (`/claudna:implement-plan` challenge round, `--auto` synthesis pass) resolve them during implementation.

The gate "passes" when:
- All generated documents have had `/adversarial-review` run (or the attempt was logged on failure).
- Findings are appended to the document body.
- The skill's summary/handoff section mentions how many `/adversarial-review` findings were raised.
