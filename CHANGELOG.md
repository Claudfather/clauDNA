### Security
- **Any-depth gitignore rules for Claude fleet bot telemetry ([Claudlobby#874](https://github.com/Claudfather/Claudlobby/issues/874)).** The existing root-anchored `/data/` rule shields only checkout-root landings; observed telemetry landings include nested paths (the hook writes relative to the session cwd, wherever that is). ### Added
- **`/audit scale` — scale-survival architecture audit lens (new `audit` lens).** A read-only, `auto: yes` specialization that evaluates whether the system survives growth — high throughput, high user counts, and multiple tenants — across processes, replicas, queues, databases, caches, external providers, and operational workflows — a field-tested distributed-systems review method generalized into repo-agnostic components (no product, vendor, broker, or hosting assumptions). Thin-router rule holds: the engine gains only a table row + `argument-hint` token (the description gains the scale-survival picker vocabulary (high throughput, high user counts, multi-tenant isolation) and drops the eight `Replaces /…-audit` breadcrumbs for skills retired back in 0.7.0 — old muscle memory has long since resolved, and the ~140 freed chars keep the full twelve-lens vocabulary under the 500-char cap); all depth lives in `skills/audit/scale/`, split by role — `scale.md` (method: isolation-boundary + authoritative-identity definition, a five-class evidence discipline separating `repository-proven` from `documentation-only` / `external-assumption` / `proposed` / `unverified` claims, a read-only `<HARD-GATE>`, four parallel discovery subagents + a failure-window convergence pass), `scan-categories.md` (eight checklists A–H mirroring the scorecard, including two machine-checked regex blocks for fail-open interfaces and distributed queue/worker hazards), `failure-windows.md` (twelve cross-process failure shapes — replay, broker loss after outbox publish, delayed wake-up loss, lease expiry vs. stale worker, cancellation racing an in-flight effect, ambiguous provider responses, rolling restarts, poison regeneration, missing RLS context on pooled connections, one-tenant flood, shared limiter/coordination-store outage, post-recovery retry herd — each demanding a concrete ordered sequence, never a generic warning), `report-template.md` (a stable ten-section output contract: executive verdict, eight-dimension scorecard, boundary-and-capacity map, evidence audit, failure sequences, P0–P3 findings carrying severity/confidence/concern/evidence/consequence/sequence/remediation, required invariants, acceptance-test matrix, open decisions, and an unverified-claims ledger; P0–P3 map onto the shared `priority:*` labels so `--output github` stays format-compatible with every other lens), and `subagent-prompts.md`. Routing is deliberately conservative: the positive triggers (tenant/org/workspace/account isolation, replicas, queues/workers/leases/outboxes, RLS, tenant rate limits and fairness, tenant migrations/backfills, effects via tenant-owned credentials) are balanced by explicit negative triggers — a bare `tenant_id` column is declared a non-trigger on both the engine row and the lens, with confusable requests pointed at `/audit security` / `tech-debt` / `access-path` / `data-model` / `investigate-app` — and mixed evidence defers to the engine's print-the-table-and-stop ambiguity rule. **Built as a pressure tester, not just a correctness checker:** Phase 0 demands a declared capacity envelope — provisioned vs. active tenants, peak admission rate, shared budgets, and every SLO with an unambiguous measurement point — whose *absence is itself a finding* (an unstated scale target is unfalsifiable; the audit then derives a conservative envelope and says so); scan category E audits saturation backpressure (fast reject/defer with bounded latency vs. unbounded queues and full-timeout hangs), bounded+jittered retries vs. post-recovery herds, atomic all-or-none multi-bucket admission, the declared degraded-mode policy for limiter-store outages, and queue-age-not-CPU autoscaling signals; and the acceptance-test matrix mandates one saturation row per shared budget at the envelope's declared peak. Deterministically pinned by `tests/test_scale_lens.py` (31 tests): lens registration + a thin-engine check (lens-depth tokens like `BYPASSRLS`/`fencing` may not leak into the router), positive/negative/ambiguous routing against `tests/fixtures/scale/routing-cases.yaml`, the stable report structure, and the machine-checked patterns against three golden fixtures — a fail-open repository (optional tenant filtering, conditional scoping, nullable ownership, global prefix lookup, a `tenant_id=None` maintenance path) that must trip every fail-open pattern, a correctly fail-closed repository (mandatory context raises, tenant-composite keys, audited maintenance interface) that must trip none, and a distributed queue/worker (re-claimable `processing` rows, unfenced finalization, tenant-unscoped idempotency key, blind retry after an ambiguous timeout, process-local limiter, unjittered fixed-interval poll) that must trip every queue pattern. **Review-hardened so each heuristic tells the bug from its fix** (PR #314 review): the fencing pattern rejects fenced predicates (`… AND lease_token = %s` no longer matches — the original matched its own fix), the blind-retry pattern requires a call shape (a `# never blind retry` comment no longer trips it), the limiter pattern generalizes the class-name alternation and names its coverage limit, the inline-idempotency pattern is labeled a lead (a correct `build_idempotency_key(job)` helper still needs its body traced); a fourth golden fixture — `queue_worker_fenced.py`, the correct worker (token-fenced finalization + stale-write detection, tenant/namespace-scoped key, reconcile-not-retry ambiguity handling, injected shared limiter, jittered polls) — joins the fail-closed repository (which gains the tenant-namespaced prefix-lookup mirror) as a no-false-positive control that would have caught the fencing defect; ambiguous routing rows are screened against the lens's *full* positive-trigger vocabulary rather than the curated per-row anchors (one utterance smuggling the declared `accounts` trigger was reworded); and `--auto` gains an explicit confidence floor — a `low`-confidence, pattern-only lead never files as P0/P1. **Named `scale`, not `multi-tenancy`** (the working name through review): the lens's question is scale survival, with tenancy one dimension of it — Phase 0 defines the isolation unit (in a consumer product the individual user account is a tenant of size one), grades the isolation-specific dimensions `N/A` when a system genuinely has none rather than scoring an absent boundary as safe, and blocks only when there is neither an isolation unit nor a scale-out surface; routing adds growth/high-throughput positive triggers and a single-endpoint-profiling negative trigger (performance engineering routes to `/audit system` or `frontend-perf`). Three new routing-matrix rows anchor the picker-level vocabulary; `make check` stays green.
- **`/audit data-model-redesign` — ground-up data-model redesign evaluation (new `audit` lens).** A sibling of `data-model` (which stays the fast fit-audit — both lenses cross-reference each other in the engine table and their opening paragraphs, partitioning the intent space: fit of the model *as it stands* vs whether it should be *replaced* and what replacing it costs). Generalizes the seven-part methodology from a real single-system evaluation into a stack-neutral lens: (1) reconstruct the system as built **before any critique** — including the load-bearing consumer inventory; (2) source-of-truth-per-concept inventory (authoritative home, every copy, sync mechanism, can-they-disagree); (3) path traces with transaction boundaries (what commits together, what can partially fail); (4) evaluation; (5) comparison of **≥3 candidate approaches with incremental repair mandatory among them** — the null-redesign baseline every rebuild must beat, on one shared criteria matrix; (6) recommendation **last**, argued strictly from the matrix; (7) an expand → backfill → dual-write → shadow-read → cutover → contract migration plan with a per-consumer coverage matrix (every Part-1 consumer has a disposition at every stage; "unaffected" is a recorded disposition, never an omission) and a rollback entry (trigger/mechanism/blast-radius) per stage — contract, not cutover, is the point of no return. Interactive-only (`auto: no`; the engine owns the `--auto` blocked-result path per lens-contract §4): two human gates — reconstruction confirmation (reconstruct-before-critique is a `<HARD-GATE>`) and direction choice (the migration plan is cut only for the chosen direction, and recommendation-last governs the *presentation* order too). Three reference files: `evaluation-prompt-template.md` — the generalized **neutral** prompt dispatched to fresh-context evaluators, with a **leakage-scan rule** run on every filled prompt before every dispatch (strip named destinations, verdict adjectives on the current model, the requester's suspected fix, imported conclusions, outcome-presupposing phrasing — a leaked prompt returns the requester's opinion with citations); `migration-playbook.md` — the six-stage discipline (never break the readers; every step independently shippable and reversible; move the source of truth last), with explicit backfill/dual-write reconciliation, shadow-read divergence gating, and adaptation rules (incremental repair uses the same staging in miniature; skipped stages are named and justified, never silent); `verification-checklist.md` — a **mechanical** pre-handoff gate run in every output mode (cited files resolve at the audited revision, cited issues resolve via `gh` with `--state all`, placeholder-debris scan, tracker reconciliation bucketing net-new/extends/regressed/duplicate/already-landed, plus internal-consistency list-diffs: ≥3 candidates with repair present, consumer inventory ↔ coverage matrix diffed both ways, rollback per stage). Lens dir `skills/audit/data-model-redesign/`; engine table row + `argument-hint` token added, description reworded to "data model fit and redesign" with every routing-fixture keyword intact — and the engine's hardcoded lens/concern counts ("across ten concerns", "ten concern lenses") are **dropped, not incremented**, per the house rule that a hardcoded count rots on the next add/remove (the #273 sweep's precedent), which also leaves description-budget headroom for the next lens instead of spending it; `--output docs` routes to the existing `documentation/planning/data-model/<session>_<date>/` convention (registry row added in `documentation-standard.md` §2, noting the directory is shared with the fit lens); README's `/audit` row refreshed to the full lens set (it had lagged, missing `system` and `cache`). Orchestration follows the house disk-write pattern (subagents write scratch, orchestrator reads only at the two gates) with redactor scrubs at every file handoff (orchestration-guide §7); findings carry the shared `data-integrity`/`architecture` concern vocabulary — no new concern minted (lens-contract §3). Covered by `tests/test_data_model_redesign_lens.py` — lens registration (table row, `argument-hint` token, sibling cross-references, thin-router token check), the seven-part protocol's structure and ordering rules, template-variable closure (every `{{var}}` declared ↔ used) plus the leakage-scan rule's five categories, the playbook's stage order / backfill requirements / per-stage rollback triple, and the verification checklist's check-set — plus a `routing-matrix.yaml` row anchoring "data model" + "redesign" so CI proves the redesign question routes past the fit sibling. - **`/recall` re-reads the harness `MEMORY.md` snapshot on every recall.** The harness injects a project's `memory/MEMORY.md` once at session start — a frozen snapshot that misses topics that only turn relevant later and never re-fires when a sibling session or `/capture`'s fallback writes to it mid-session. Recall now re-reads it live (score the index lines against the query, render a `### This project — harness memory` tier, read linked topic files under `--full`) — a substrate separate from the Claudron vault, additive on both the engine and INDEX-fallback paths. **The directory is resolved, not reconstructed.** The harness keeps auto-memory at a cwd-derived default (`~/.claude/projects/<cwd-slug>/memory`) only until something sets `autoMemoryDirectory` — and Claudlobby sets it on every composed bot, pointing outside `~/.claude/` entirely. Rebuilding the default path therefore looked in a directory that exists on no fleet bot, found nothing, and skipped silently: the feature no-opped in the environment it ships into, while passing on any un-redirected box. Resolution is now mechanical — a bundled `scripts/resolve_memory_dir.py` reads the setting across the settings chain (user → project → project-local, nearest setter wins, `CLAUDE_PROJECT_DIR` authoritative when the harness exports it) and falls back to the derived default only when nothing redirects; `skills/recall/SKILL.md` invokes it under the same `${CLAUDE_PLUGIN_ROOT}` + cache-glob convention as `redact.py`. The ancestor walk is load-bearing rather than defensive: a bot's settings live in its own directory while skills run with the cwd inside a repo checkout below it, so consulting only `./.claude/` reads the *repo's* settings and never the bot's. Covered by `tests/test_resolve_memory_dir.py` (13 tests), whose fixtures build the **redirected** fleet-bot topology rather than the default one — a test that only exercises the default cannot distinguish the two implementations, which is precisely how the reconstructing version passed review. Mutation-checked: reverting the resolver to the reconstructing behaviour fails 10 of the 13.

### Considered and declined

Structurally the two are different tools (kindle: universal, hard-gated, interactive-only, no `--auto`; product-vision: a specific architecture-grounded codebase-opportunity report generator with full `--auto` + GitHub Issue output). Initial recommendation was to leave kindle unported — it sits in the same vendored-Superpowers-lineage category (`finishing-a-development-branch`, `systematic-debugging`, etc.) clauDNA deliberately does not duplicate — but porting it as its own new skill (not a product-vision rebrand) is a materially different, smaller-risk decision, and once asked directly, was approved. See the `/kindle` entry above for what actually shipped and how it was scoped down from the full upstream skill.
- **`adversarial-self-check` (artemis-skills) declined — a boundary judgment, not a quality one.** Confirmed distinct from `/claudna:adversarial-review` (that lens critiques a *document*; this fires on the *agent's own live in-flight decision* via a genuinely separate fresh subagent) but has zero clauDNA- or software-engineering-specific content — a domain-agnostic decision-hygiene discipline of exactly the shape as the eight vendored Superpowers-lineage skills already present in artemis-skills' roster and consistently absent from clauDNA's by design (this session's own `using-superpowers`/`superpowers:*` skill listing is the live proof clauDNA's environment already sources that lane from a separate plugin rather than reimplementing it). Not ported.
- **`/build-all` — governed multi-phase epic runner, heisted from artemis-skills.** New skill for driving an epic's worth of phase docs as one ordered run (a `forge` epic ready for execution, or any directory of ordered plan docs) with the cross-phase state no single-phase skill can see: a Sprint Ledger, an invariant registry re-checked every phase, a merge-topology plan (the squash + stacked-branch conflict is structural, not bad luck), deploy-reachability tracking (merged is not live), and a governed review-convergence loop with a mandatory class sweep (fix the pattern a finding came from, not just the cited instance) and measure-before-asserting discipline on population claims. Composes existing skills rather than replacing them: `/claudna:worktree` (isolate) → `/claudna:build` (implement) → native `/simplify` → `/claudna:verify-completion` → `/claudna:commit-push-pr` (ship), per phase. Adapted from artemis-skills' `build-all` (itself derived from a real nine-doc, 8-PR, two-repo epic that shipped green-but-wrong twice before this process existed) — its Artemis-specific skill references (`ship`, `dispatching-parallel-agents`, `subagent-driven-development`) are remapped to clauDNA's equivalents (`commit-push-pr`, `worktree`, in-session subagent decomposition) or dropped where clauDNA has no equivalent.

### Changed
- **`synthesis-contract.md` rewritten to junction-keyed decisions, heisted from artemis-skills' evolution of this clauDNA-originated contract.** The `weigh-development-paths --auto` → `build --auto` handoff previously carried `decisions_resolved`/`decisions_unresolved` as bare integer counts and a 2-outcome producer (`completed`/`blocked`, with the consumer always remapping `blocked` to its own `needs-input`). The new schema is junction-keyed — each resolved/unresolved decision is an object (`{junction, choice, rationale}` / `{junction, why}`) naming *which* decision and *why*, not just how many — and the producer gains a genuine 3-way outcome: `completed`, `needs-input` (a junction hinges on a human value/policy/security call the 7-dimension matrix can't settle — a **technical tie is still `completed`**, the matrix must still pick), and `blocked` (a contract error — malformed/empty bundle — not a decision gap). `build`'s Step 3-AUTO remaps both `needs-input` and `blocked` to its own `needs-input` unconditionally — never silently falls back to implementing an unresolved decision. The input bundle shape (previously undocumented in the contract itself, and duplicated with drift risk between `weigh-development-paths`' "Input contract" section and `build`'s "Write the bundle" step) now lives once in the contract as a unified `## Open decisions` section with `### D<n>` junction blocks tagged by source (`adversarial finding` / `matrix decision point` / `plan fork F<n>`) — both consuming skills point at it instead of restating it. ### Security
- **Permission-prompt bypass via a lone `&` in the PreToolUse hook ([#258](https://github.com/Claudfather/clauDNA/issues/258), HIGH).** `plugin-hooks/pretooluse-permissions.sh`'s `split_commands()` decomposes a compound command into the parts that will actually run, then auto-approves only if every part matches a user allow-glob. It split on `&&`, `||`, `|`, `;` but treated a lone `&` (background operator) as a literal character — so `git status & rm -rf /` validated as **one** token against a trailing-wildcard glob like `Bash(git *)` and was approved wholesale, silently skipping the write-safety prompt that is the human's last checkpoint against an injected command. Now a lone `&` splits like `;` — each side must match on its own or the whole command prompts. The `&` is kept literal inside a redirection (`2>&1`, `>&`, `<&`, `&>`), where it is fd-duplication rather than a control operator, so the fix adds no spurious prompts to the most common shell idiom. Regression-tested against the exploit table and the redirection forms (`tests/test_pretooluse_permissions_hook.py`, 12 cases).
- **AppleScript/shell injection in the notification hook ([#259](https://github.com/Claudfather/clauDNA/issues/259), MEDIUM).** `plugin-hooks/notify.sh` read raw stdin and interpolated it, unescaped, into the AppleScript *code* string passed to `osascript` — so a notification `message` containing a `"` and a newline could close the string literal and inject `do shell script "…"`, i.e. arbitrary command execution (macOS). Interpolating the whole raw JSON payload also broke the notification for ordinary input, since JSON always contains quotes. The hook now extracts the `message` field with `jq` and passes it as a run-*argument* bound to an AppleScript variable — data, never code; the `-e` fragments are static. Verified with a recording `osascript` shim that the injection payload reaches only the argument vector, never a code fragment, and never executes (`tests/test_notify_hook.py`, 5 cases).
- **Hook input-hardening: unvalidated `session_id` path and unescaped telemetry slug ([#260](https://github.com/Claudfather/clauDNA/issues/260), LOW, defense-in-depth).** `plugin-hooks/precompact-reflect.sh` placed the hook's `session_id` directly into a `/tmp` marker path; a `/`-bearing value could escape the marker dir. It is now validated to `[A-Za-z0-9._-]` before use and a malformed id fails open like a missing one. `plugin-hooks/telemetry-emit.sh`'s jq-less fallback hand-builds a JSON line from the skill slug; the slug is now guarded to `[A-Za-z0-9:_-]` (a stray backslash would otherwise emit an invalid JSON escape) and a non-conforming slug drops the event rather than writing corrupt telemetry. Neither was exploitable today (`session_id` is a Claude-Code UUID; the slug arrives quote-free); the guards pin the boundary against a future provenance change (`tests/test_hook_input_hardening.py`, 5 cases). All three findings from the v0.17.0 rolling security audit.

Claudron removed the bare name outright in its 0.3.0 (`CLAUDRON_VAULT` is dead; the engine names it on stderr when a stale export is what's confusing you), so continuing to honor it here would re-create that hazard pointing the other way. The ladder is now `CLAUDRON_VAULT_PATH` → `SHARED_DOCS_PATH` (the latter fallback-mode only, never consulted once an engine is detected), stated in **one** place — `skills/_shared/documentation-standard.md` §10 — which now *points at* [Claudron's `docs/CLI_CONTRACT.md` §Environment](https://github.com/Claudfather/Claudron/blob/main/docs/CLI_CONTRACT.md#environment) as the owner rather than restating the order (register rule R3: consumers conform, never fork). Seven files had independently described the ladder; `skills/claudron/status.md` was additionally telling users to `export CLAUDRON_VAULT=<path>`, and `skills/_shared/claudron-engine.md` asserted "the CLI resolves the vault from `CLAUDRON_VAULT`" — false as of Claudron 0.3.0. The dead name: assignment (`CLAUDRON_VAULT=…`, with or without `export`) *or* imperative prose ("Set `CLAUDRON_VAULT` to…"), with each surviving mention required to say the name is removed *near* the mention rather than anywhere on the line. And a **restated ladder**: enumerating both env names on one line is itself the violation, whether or not §10 is cited — the regression this rule was written for cited §10 in the very sentence that contradicted it, saying "in that order" where §10 says the names are mode-selected and explicitly "not a precedence chain". The gate borrows `validate-skills.py`'s file-type scope, so `.sh` files and the templates shipped into user projects — the only surfaces that could *actually read* an env var — are in scope; it keeps its **own** exclusion list, because the removed-skill-names exemptions do not transfer to an env var. The live `skills/cleanup-legacy-install/` is therefore gated here, while point-in-time records (plans, specs, decisions, archive, and this changelog) stay exempt — they describe the ladder as it stood when written, and rewriting them would falsify the record rather than fix a bug. **If you export `CLAUDRON_VAULT`, rename it to `CLAUDRON_VAULT_PATH`.**

Absent field ⇒ pre-0.3.0.
